# API reference: GitHub and GitLab

The baseline for the framework's forge wrappers (`src/payload/scripts/github_wrapper.py`,
`src/payload/scripts/gitlab_wrapper.py` and the copies that projects grow from them). The wrappers talk to the forges
over plain HTTPS, with no `gh` or `glab` CLI and no MCP server, so that a token can be scoped to one repository and
the wrappers work wherever Python runs. This folder lists what they can call: every REST endpoint with all of
its parameters, every GraphQL query, mutation and type, and the mechanics shared by all calls: authentication,
headers and versions, encoding, pagination, uploads, downloads, rate limits and errors.

The generated `README.md` files carry the current numbers and the exact source pins.

### What "complete" means here, and how it was checked

- GitHub REST is generated from GitHub's own OpenAPI description, which defines the API for api.github.com. Every
  operation, every path and query parameter, and every request-body field is rendered. The request-body fields
  are flattened through nested objects, arrays and `oneOf`/`anyOf` variants.
- GitHub GraphQL is generated from the public schema (SDL): every type, field, argument, input field, enum value
  and directive.
- GitLab publishes no complete machine-readable REST description. Its OpenAPI v2 file covers 1,150 operations;
  the docs pages cover more. The REST reference is therefore built from the docs pages. Each section that names
  an endpoint in a code block becomes an entry, and its attribute tables become the parameters. The OpenAPI file
  is used for cross-checking: it adds enums, defaults and file-upload markers to matching entries, and its
  operations that no docs page names are listed in `rest/openapi-only.md`. The reference is the union of both
  sources.
- GitLab GraphQL is generated from the reference pages GitLab generates from its schema. Connection and edge
  types, which those pages collapse to one line, are restored with their standard fields.
- After generation, independent scans of the raw sources were compared with the output. All 1,272 GitHub
  operations were found, with their 3,661 parameters and 1,284 top-level body fields. So were all 1,824 GitHub
  GraphQL definitions with every enum value, every endpoint line of the GitLab docs pages, all 1,150 GitLab
  OpenAPI operations, and every type, query and mutation heading of the GitLab GraphQL reference. All 34,000+
  relative links and anchors resolve.

## Reading the generated tables

### REST, both forges

- The heading is the vendor's title for the operation. The line under it gives `METHOD path` and a link to the
  official page, which has the prose, the examples and the response bodies. Descriptions are not copied here.
  Only facts are kept: types, required flags, defaults, allowed values, constraints, deprecations, tiers.
- **Required** means required within its parent. For a nested body field, that is the parent object.

### GitHub REST specifics

- **operationId** is GitHub's stable name for the operation, for example `issues/create`.
- **Host** appears only when the operation uses a different host, for example `uploads.github.com` for release
  assets.
- **Paging** names the mechanism: `page`/`per_page`, or cursor-based with `before`/`after`/`cursor`. It also says
  where the items are: the response body itself, or the named array property of a wrapper object such as
  `workflow_runs`. It mentions when the `Link` header is declared.
- **Responses** lists every status code, with its media type and the schema component it returns (for example
  `issue` or `basic-error`).
- **Media types named in the docs** lists the custom `Accept` media types the operation's description mentions
  (raw, html, text, full, diff, patch, …).
- **Notes** can say: deprecated, with dates; not available to GitHub App installation tokens; triggers
  notifications (content-creation secondary rate limits apply); or the body may be a bare JSON array.
- **API version `2026-03-10`** lists what changes for the operation when a client sends
  `X-GitHub-Api-Version: 2026-03-10` instead of `2022-11-28`.
- Body field paths:

  | Path | Means |
  |---|---|
  | `a.b` | Field `b` of object `a` |
  | `a[]` | The items of array `a` |
  | `a[].b` | Field `b` of each item of `a` |
  | `a.*` | Any key of the map `a` |
  | `a{name}.b` | Field `b` when `a` has the variant shape `name` (a `oneOf`/`anyOf` member) |
  | Type `constraint` | Which required sets the `oneOf`/`anyOf` demands |

### GitLab REST specifics

- Paths are relative to `https://HOST/api/v4`. Placeholders are written `:name` or `*name` (`*` may contain
  slashes). A path that starts with `https://HOST` is at the instance root, for example the OAuth endpoints.
  `<route-prefix>` (package registries) is spelled out at the top of its page.
- **In** is inferred: `path` when the path has that placeholder; `query` for GET/HEAD/DELETE; `body` for
  POST/PUT/PATCH; `form` for file uploads (`multipart/form-data`). GitLab accepts body attributes as form fields or
  JSON, and also as query parameters.
- **Values**: `one of:` is an enum from GitLab's OpenAPI file. Otherwise the column holds the literals the docs
  name in backticks for that attribute, which can include examples.
- **Notes** can say: tier limits (`Premium and Ultimate only`); deprecated, with version; `since X.Y`;
  `excludes` (mutually exclusive attributes); conditionally required; file upload; or `in OpenAPI only`, for an
  attribute the OpenAPI file lists but the docs table does not.
- **Availability** gives the tier, offering and status of a section when they differ from its page's.
- **Response attributes** lists the response fields and their types, where the docs list them in a table.

### GraphQL, both forges

- Types link to their definition. `T!` is non-null and `[T]` is a list.
- Arguments are written inline as `name: Type = default (notes)`.
- A mutation's section includes its input type and payload type when no other operation uses them. Those types are
  then not repeated in the type files.
- **Notes** can say:
  - deprecated, with the removal date and replacement names for GitHub, or the version for GitLab
  - `preview`
  - `ID of: …`, for an `ID` argument that must refer to one of the listed object types
  - `category`, GitHub's docs category
  - experiment, beta or `since X.Y` (GitLab)
- GitLab's reference does not name mutation payload types. They are written `<Mutation>Payload` here, following
  GitLab's naming convention.

## Deliberately not here

- **Prose:** the vendors' descriptions and examples. Every entry links to its official page.
- **Full response bodies:** GitHub entries name the response schema component. GitLab entries list response
  attributes where the docs do.
- **Webhook payloads:** GitHub's OpenAPI file carries them under `x-webhooks`, and GitLab documents webhook events
  outside `doc/api`.
- **GitHub Enterprise Server and Enterprise Cloud variants:** GitHub publishes separate descriptions for them
  (`ghes-*`, `ghec`). Only api.github.com is covered, which includes the organization-level and some
  enterprise-level endpoints.
- **Fine-grained token permissions per GitHub endpoint:** they are not in the OpenAPI file. See
  [`github/conventions.md`](github/conventions.md).

## Regenerating

The sources are downloaded into the git-ignored `tmp/api-sources/`, one folder per source, and are only read, never
executed. Pin each one to a commit and record the pins in `tmp/api-sources/pins.json`.

```bash
mkdir -p tmp/api-sources/github-openapi tmp/api-sources/github-graphql tmp/api-sources/gitlab-openapi tmp/api-sources/gitlab-docs-zip tmp/api-sources/gitlab-docs
```

```bash
curl -sSfL -o tmp/api-sources/github-openapi/api.github.com.json "https://raw.githubusercontent.com/github/rest-api-description/<commit>/descriptions/api.github.com/api.github.com.json"
```

```bash
curl -sSfL -o tmp/api-sources/github-graphql/schema.docs.graphql "https://docs.github.com/public/fpt/schema.docs.graphql"
```

```bash
curl -sSfL -o tmp/api-sources/gitlab-openapi/openapi_v2.yaml "https://gitlab.com/gitlab-org/gitlab/-/raw/<commit>/doc/api/openapi/openapi_v2.yaml"
```

```bash
curl -sSfL -o tmp/api-sources/gitlab-docs-zip/doc-api.zip "https://gitlab.com/api/v4/projects/gitlab-org%2Fgitlab/repository/archive.zip?path=doc/api&sha=<commit>"
```

The zip has one top folder (`gitlab-<commit>-<commit>-doc-api/`). Unpack it so that the pages end up at
`tmp/api-sources/gitlab-docs/doc/api/`:

```bash
python -I -c "import zipfile, sys; z = zipfile.ZipFile(sys.argv[1]); [z.extract(m, sys.argv[2]) for m in z.namelist()]" tmp/api-sources/gitlab-docs-zip/doc-api.zip tmp/api-sources/gitlab-docs
```

```bash
mv tmp/api-sources/gitlab-docs/gitlab-*-doc-api/doc tmp/api-sources/gitlab-docs/ && rmdir tmp/api-sources/gitlab-docs/gitlab-*-doc-api
```

`pins.json` holds what the generated READMEs print as provenance: `github_rest`, `github_rest_url`,
`github_graphql`, `github_graphql_url`, `gitlab`, `gitlab_docs_url` and `gitlab_openapi_url`. Then build and verify:

```bash
python -I scripts/api_reference/build.py --sources tmp/api-sources --out docs/api-reference
```

```bash
python -I scripts/api_reference/verify.py --sources tmp/api-sources --out docs/api-reference
```

`verify.py` repeats the completeness and link checks described above, and exits non-zero when anything is
missing.
