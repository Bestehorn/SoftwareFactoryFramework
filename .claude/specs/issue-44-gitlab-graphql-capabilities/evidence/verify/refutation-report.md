## Refuted

- **M2j** (AC-2.2): G's `test_every_record_is_called_through_main` plans two pages or one answer from `record.connection`. Q's `_connection_problems` judges only a record that has a connection. So no test ties a document that selects `after: $after`, `nodes` and `pageInfo` to a connection. Under 2j, `call graphql#Group.vulnerabilities` prints the first page's `data`, not AC-2.2's array of every node. Only `graphql#Project.workItems`' paging is pinned.
- **M2k** (AC-1.1, task 2.3): G builds its argv from `registry.variables` and its expected `query` from the record's own document, and Q checks reference validity only. D1's `$input` shape is pinned for `graphql#workItemUpdate` alone (`test_a_variable_holds_the_given_json_value`). Under 2k, the usage's form `-F input=...` exits 2 for `graphql#branchRuleDelete`. This is the class of #30's M2c.
- **M2r** (AC-3.1): no test gives `-f`/`-F` and `--file` for one name. Inverted, a call that names a file for every Upload value posts JSON holding the `-F` value instead of AC-3.1's multipart request.
- **M3f** (AC-5.1): the capability lines satisfy the `REFUSED_IDS` clause of `test_the_usage_names_every_graphql_record`, and any sentence satisfies `exit 2`. So the clause cannot fail while `capability_problems` passes, and the refusal statement can go.
- **COV** (AC-3.1): registry.py line 279 runs in no test; see the COV row.
