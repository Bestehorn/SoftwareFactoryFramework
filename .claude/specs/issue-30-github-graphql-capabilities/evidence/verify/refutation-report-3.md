## Findings

C3 survives every test in P, and it is not equivalent. The `input-beside-a-variable` row's patterns are `--input`, `-f/--raw-field` and `-F/--field`. `refuse_graphql_raw_body`'s message matches all three ("...its variables are JSON, given with -f/--raw-field or -F/--field"), so on `graphql/pinIssue` the row cannot tell the two refusals apart. An in-memory probe (no file changed, transport `None`) called `_call_graphql` with `-F input={}` and a raw body, as written and with `refuse_both_bodies` made a no-op. As written, each of `graphql/pinIssue`, `graphql/transferIssue`, `graphql/enablePullRequestAutoMerge` and `graphql/noSuchRecord` logs `call refuses --input together with -f/--raw-field or -F/--field: ...`. Under C3 every call still exits 2, but `graphql/transferIssue` logs `...: no subcommand sends it`, `graphql/enablePullRequestAutoMerge` logs `...: use the merge-pr subcommand`, and `graphql/noSuchRecord` logs `No GitHub GraphQL record declares "graphql/noSuchRecord"`. None of the three names either input. That breaks #46 AC-1.3 ("write a message naming both inputs") on the GraphQL path, and the order DL-009 and the `call.py` docstring state. No test runs a gated or undeclared GraphQL ID with both inputs, and none matches text that only `refuse_both_bodies` writes.

The first harness pass marked K2 SURVIVED because of R's teardown error. The kill rule was corrected to "a FAILED line and no collection error", and every mutant re-ran. The capture is that second pass, and its counts match the first.
