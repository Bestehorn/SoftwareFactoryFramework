# Best-practice review — issue #43 design, iteration 01

No documentation MCP server covers GitLab. Sources: GitLab `master` (workhorse and `lib/api`), Grape `master`, npm/cli `latest`, docs.gitlab.com, all read 2026-11-11.

### A1 — npm "Create or update a dist-tag" sends `version` where GitLab does not read it
Severity: A
Location: design.md § D5 (table), § D6 `Param.location`; requirements.md AC-1.4, AC-4.2
Defect: D6 makes the `version` row a `Location.BODY` `Param`, so `call` sends the object `{"version": "1.0.0"}` (`transport.py`, JSON body). But GitLab reads the version as the whole parsed request body: in the dist-tags `put` of `lib/api/concerns/packages/npm_endpoints.rb`, `version = env['api.request.body']`, and Grape's `formatter.rb` `read_rack_input` stores the parsed body there. So the version GitLab looks up is the object, never `1.0.0`. `npm dist-tag add` sends `body: JSON.stringify(version)` with `content-type: application/json` (npm/cli `lib/commands/dist-tag.js`).
Material-because: wrong-behaviour — under every prefix, `package#create-or-update-a-dist-tag` cannot tag the version the caller names.
Proposed-edit: add a row to D5's table: "`package#create-or-update-a-dist-tag` (npm) | project: `` apiProjectPattern+`/packages/npm/-/package/[^/]+/dist-tags/[^/]+` `` → `proxy`; group and instance: the catch-all `proxy`; Rails reads the version as the whole body (`version = env['api.request.body']`) | raw body, JSON: the version as a JSON string (`"1.0.0"`), as `npm dist-tag add` sends it". Change D5's `content_type` bullet to "but npm's two records', which are `CONTENT_TYPE_JSON`". D6's raw-body rule then makes `version` a query `Param`. Add npm "Create or update a dist-tag" to AC-4.2's raw-body list, restated the way DL-004 restated it. Give F `test_a_raw_upload_sends_the_bytes_as_its_body` a row for it under `--route-prefix /projects/:id/packages/npm`: `PUT /api/v4/projects/<project_id>/packages/npm/-/package/pkg/dist-tags/stable`, `application/json`.

### B1 — NuGet v3 "Upload a package file" does not reach `mimeMultipartUploader`
Severity: B
Location: design.md § D5 (the NuGet row); requirements.md AC-4.2
Defect: the record's path, `PUT /projects/:id/packages/nuget` (verbatim per AC-1.1), has no `/` after `nuget`. The routes.go patterns are `` apiProjectPattern+`/packages/nuget/` `` and `` …`/packages/nuget/v2` ``, matched against `urlprefix.CleanURIPath(r.URL.EscapedPath())`, which adds no `/` (`upstream.go`, `urlprefix.go`). So the request falls to the catch-all `proxy`. Rails then refuses the part (`nuget_project_packages.rb` `file_params`: `requires :package, type: ::API::Validations::Types::WorkhorseFile`), because `WorkhorseFile.parse` raises unless the value is an `UploadedFile`, and `Gitlab::Middleware::Multipart#call` passes through unchanged any request without Workhorse's `Gitlab-Workhorse-Multipart-Fields` header. docs.gitlab.com's NuGet example uploads with a PUT to `…/projects/1/packages/nuget/`.
Material-because: AC-4.2 contradicted — the design sends this upload "in the form GitLab Workhorse reads on its route", but on this path Workhorse rewrites no part.
Proposed-edit: split D5's NuGet row in two: "`package#upload-a-package-file-5` (NuGet v3) | `` apiProjectPattern+`/packages/nuget/` `` needs the `/` after `nuget` that the row's path lacks: the catch-all `proxy` | `--file package=…`" and "`package#upload-a-symbol-package-file` | `` apiProjectPattern+`/packages/nuget/` `` → `mimeMultipartUploader` | `--file package=…`". Name `package#upload-a-package-file-5` in C1's Residual.

### C1 — The source already decides the catch-all-proxy uploads; they need not wait for #11
Severity: C
Location: design.md § Residuals (the `package#upload-a-package` / `avatar` bullet)
Defect: that bullet leaves "whether GitLab takes their part" to #11. The sources settle it. The Maven virtual-registry upload "is accessible only by GitLab Workhorse" (docs.gitlab.com Maven virtual registry API, "Upload a package"; in `ee/lib/api/virtual_registries/packages/maven/endpoints.rb`, `post 'upload'` calls `require_gitlab_workhorse!`). `avatar` is a `WorkhorseFile` (`lib/api/helpers/projects_helpers.rb` `optional_project_params_ce`), which no part sent through `proxy` satisfies (B1's sources).
Proposed-edit: replace the bullet with: "`package#upload-a-package-file-5`, `package#upload-a-package` and the `avatar` of `package#change-the-visibility-of-the-container-registry` reach Rails through Workhorse's catch-all `proxy`, so GitLab refuses their `WorkhorseFile` part, and `package#upload-a-package` is Workhorse-only (`require_gitlab_workhorse!`). The records stand for AC-1.1, but no `call` uploads through them → one findings-ledger row."

### C2 — Five package families do not read the credential the transport sends
Severity: C
Location: design.md § Security Considerations ("What stays callable", the Conan-token bullet), § Residuals (last bullet)
Defect: when an API declares `authenticate_with`, GitLab uses only those locators (`lib/gitlab/auth/auth_finders.rb` `resolve_access_token`). Debian (`debian_package_endpoints.rb`), NuGet (`nuget_project_packages.rb`, plus `X-NuGet-ApiKey` on publish) and Helm (`helm_packages.rb`) accept HTTP Basic only. Ruby gems accepts a bare `Authorization` token or Basic (`rubygem_packages.rb`; `token_locator.rb` `http_token` declines a `Bearer` value). Conan reads only its own JWT or Basic (`helpers/packages/conan/api_helpers.rb` `access_token_from_request`; `find_oauth_access_token` is empty). None of them reads `PRIVATE-TOKEN`, `JOB-TOKEN` or `Authorization: Bearer` (`transport.py` `TOKEN_HEADERS`). So these calls reach GitLab unauthenticated, and `package#create-an-authentication-token` and `…-1` answer 401 (`conan/shared_endpoints.rb`: `unauthorized! unless token`) instead of printing a JWT. The Terraform upload reads the `PRIVATE-TOKEN` and `JOB-TOKEN` headers but not Bearer (`terraform/modules/v1/project_packages.rb`). conventions.md "Other package formats" already warns that these formats authenticate differently.
Proposed-edit: replace the Conan-token bullet with: "`package#create-an-authentication-token` and `…-1`: Conan reads only its JWT or HTTP Basic, so with the configured header GitLab answers 401 and issues no token". In the last Residual, delete "and the Conan tokens that `package#create-an-authentication-token` and `…-1` print" and its row. Add the Residual: "The Conan, Debian, NuGet, Helm and Ruby gems routes read no header the transport sends (only Basic, a Conan JWT, `X-NuGet-ApiKey` or a bare `Authorization` token), so their calls are unauthenticated and a write is refused. An HTTP Basic credential form is outside this change (UB-2) → one findings-ledger row."

Confirmed against source: every other D5 route and handler. npm publish does take the JSON document as a raw body on `` apiProjectPattern+`/packages/npm/.*` `` → `requestBodyUploader`; the handler declares only `package_name` and `file` (`npm_project_packages.rb`), so the `versions` query `Param` is never read and does no harm. Debian's `distribution`/`component` are declared params, which Grape reads from the query. The route-prefix values are plain RFC 3986 §3.3 segments.
